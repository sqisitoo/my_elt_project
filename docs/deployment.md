# Deploying this project

Everything below builds one environment from nothing: an AWS footprint, a Snowflake account structure, and an Airflow instance running on it. It is Terraform end to end, with two manual steps that cannot be automated away — a Snowflake bootstrap script that creates the identity Terraform itself uses, and a **second `terraform apply`** required by the way Snowflake establishes trust with S3. The second one is the interesting part; if you only read one section, read [Why two applies](#step-4--second-apply-close-the-trust-loop).

Approximate time: 40 minutes, most of it waiting for RDS.

---

## What gets created

**AWS** — VPC with two public and two private subnets, an internet gateway, security groups; an ECS Fargate cluster running one task with three containers (Airflow apiserver, scheduler, DAG processor); an RDS Postgres instance for Airflow metadata; an S3 bucket used as both data lake and remote log store; an ECR repository; five Secrets Manager secrets (a sixth holds the bastion key when that flag is on); IAM roles for the ECS agent, the task, Snowflake and GitHub Actions; and a GitHub OIDC identity provider.

**Snowflake** — databases `RAW` and `ANALYTICS`; schemas `RAW.AIR_POLLUTION` and `RAW.WEATHER`; two raw tables; an `XSMALL` warehouse; a storage integration and two external stages pointing at the S3 bucket; and the `AIRFLOW_ROLE` role plus `AIRFLOW_SVC` service user with an RSA key pair generated by Terraform.

The running cost is dominated by two always-on things: the RDS instance and the Fargate task. Everything else is either usage-priced at negligible volumes or free. The warehouse auto-suspends after 60 seconds and starts suspended, so Snowflake credits are only spent while a DAG is actually building models.

## Prerequisites

| | |
|---|---|
| Terraform | `~> 1.14` — the constraint is in `terraform/main.tf` and mirrored in the CI workflow |
| AWS | An account, and a named CLI profile. `variables.tf` defaults `aws_profile` to `my-pet-project`; set it explicitly in `terraform.tfvars` if yours differs |
| Snowflake | An account, and `ACCOUNTADMIN` on it |
| OpenWeather | An API key on a **paid** plan — the historical endpoints used here (`/data/4.0/onecall/timeline/1h` and `/data/2.5/air_pollution/history`) are not in the free tier |
| Docker | Only if you push the first image by hand instead of letting CI do it |
| openssl | To generate the Snowflake key pair |

One thing must exist before Terraform runs: **the S3 bucket holding the Terraform state**. Terraform cannot create the bucket it stores its own state in. Create it by hand, with versioning on — see the commands in [`terraform/backend.conf.example`](../terraform/backend.conf.example).

## Step 1 — Bootstrap Snowflake

Terraform manages Snowflake through a service user, so that user has to exist before the first apply. That is the entire purpose of [`terraform/scripts/bootstrap.sql`](../terraform/scripts/bootstrap.sql).

Generate an unencrypted RSA key pair. Unencrypted is deliberate and consistent: neither the Terraform provider config nor the dbt `prod` profile supplies a passphrase, and the keys Terraform later generates for `AIRFLOW_SVC` are unencrypted too.

```bash
mkdir -p keys
openssl genrsa 2048 | openssl pkcs8 -topk8 -inform PEM -out keys/snowflake_tf_snow_key.p8 -nocrypt
openssl rsa -in keys/snowflake_tf_snow_key.p8 -pubout -out keys/snowflake_tf_snow_key.pub
```

`keys/` is gitignored. Paste the contents of the `.pub` file into `bootstrap.sql` where the placeholder is, then run the whole script in Snowsight as `ACCOUNTADMIN`.

It creates the `TERRAFORM_SVC` service user with that public key, and a `TERRAFORM_ROLE` holding three grants. Each one is there for a specific reason: `SYSADMIN` to create databases, schemas, tables, warehouses and stages; `SECURITYADMIN` to create the `AIRFLOW_ROLE` role and the `AIRFLOW_SVC` user and to grant privileges to them; and `CREATE INTEGRATION ON ACCOUNT`, because a storage integration is an account-level object that neither of the other two covers.

The last statement in the script returns your organisation and account names in lower case. Those two strings go into `terraform.tfvars`.

Finally, hand the private key to the provider. The Snowflake Terraform provider takes the key as **content**, not as a path — there is no `private_key_path` in its v2 schema — and reads it from an environment variable:

```bash
export SNOWFLAKE_PRIVATE_KEY="$(cat keys/snowflake_tf_snow_key.p8)"
```

```powershell
$env:SNOWFLAKE_PRIVATE_KEY = Get-Content -Raw keys\snowflake_tf_snow_key.p8
```

## Step 2 — Fill in the Terraform config

Both files are gitignored; both have a documented example beside them.

```bash
cd terraform
cp terraform.tfvars.example terraform.tfvars   # then edit
cp backend.conf.example backend.conf           # then edit
```

Two values in `terraform.tfvars` deserve attention rather than a default. `allowed_ssh_cidrs` is the only thing standing between the internet and the Airflow UI — there is no load balancer and no auth proxy in front of it, just a security group. And `github_repository` scopes which repository's workflows may assume the deploy role; a fork that leaves it pointing at the original repository will have a CI job that cannot push to ECR.

## Step 3 — First apply

```bash
terraform init -backend-config=backend.conf
terraform apply
```

When this finishes, the AWS side is complete and the Snowflake side is *structurally* complete — databases, schemas, tables, warehouse, role, user, storage integration and both external stages all exist.

One thing does not work: **the stages cannot read S3 yet.** A Snowflake external stage reaches into your bucket by assuming an IAM role in your account. That role exists — `snowflake-s3-role` — but at this point its trust policy is a placeholder. Look at `aws_iam_role.snowflake_role` in [`snowflake.tf`](../terraform/snowflake.tf): when `var.snowflake_external_id` is empty, the policy trusts your own account root. Nothing in Snowflake can assume it, because Snowflake's IAM principal lives in Snowflake's AWS account, not yours.

The apply prints two outputs that look like shell commands. They are.

## Step 4 — Second apply: close the trust loop

**Why this cannot be one apply.** The dependency is circular. Terraform must create the AWS role before Snowflake can be told which role to assume, so the role has to exist first. But Snowflake only generates the two values that identify it — an IAM user ARN and an external ID — at the moment the storage integration is created, which is after the role. And the role's trust policy is exactly what needs those two values. Something has to be created with an incomplete trust policy and narrowed afterwards. Snowflake documents this as a manual step in its own setup guide; here it is expressed as a conditional trust policy plus a second apply, so the end state is still entirely described by Terraform.

Feed the values back and apply again:

```bash
eval "$(terraform output -raw snowflake_iam_user_export)"
eval "$(terraform output -raw snowflake_external_id_export)"
terraform apply
```

On PowerShell the outputs are shell commands for the wrong shell, so read the values and set the variables directly:

```powershell
terraform output -raw snowflake_iam_user_export     # copy the ARN out of it
terraform output -raw snowflake_external_id_export  # copy the external ID out of it

$env:TF_VAR_snowflake_iam_user_arn = "arn:aws:iam::<snowflake-account>:user/<generated>"
$env:TF_VAR_snowflake_external_id  = "<generated>"
terraform apply
```

The only change in the plan should be the trust policy on `snowflake-s3-role`: principal narrowed from your account root to Snowflake's IAM user, plus a condition requiring the matching `sts:ExternalId`. That external ID is what prevents the confused-deputy problem — without it, any Snowflake account able to guess your role ARN could ask Snowflake to assume it.

These two variables live in the environment rather than in `terraform.tfvars` on purpose: they are outputs of this configuration, not inputs a human chooses, and writing them into the tfvars file would make it look as though you were supposed to know them in advance.

## Step 5 — Verify the S3 ↔ Snowflake trust before anything else depends on it

In Snowsight:

```sql
DESC STORAGE INTEGRATION aws_storage_integration;
LIST @RAW.AIR_POLLUTION.s3_stage;
```

`DESC` should show `STORAGE_AWS_IAM_USER_ARN` and `STORAGE_AWS_EXTERNAL_ID` matching what you just put into the trust policy. `LIST` on an empty bucket returns zero rows — that is success. A permission problem produces an error, not an empty result, so an empty listing means the trust works and there is simply nothing there yet.

This distinction matters later too: a `COPY INTO` over a prefix that matches nothing is also not an error. That is why the DAG runs `dbt source freshness` immediately after the load.

## Step 6 — Get an image into ECR

The ECS task definition references `<ecr-repo>:latest`, which does not exist yet, so the service will be trying and failing to start containers. Nothing is wrong; it just needs an image.

**Through CI, which is the intended path.** Read the role ARN and put it in the repository's Actions secrets as `AWS_OIDC_ROLE_ARN`:

```bash
terraform output -raw github_actions_role_arn
```

Then push to `main`. The workflow builds the image, pushes it to ECR over OIDC — no static AWS keys are ever stored in GitHub — re-renders the task definition with the new image **digest** for all three containers, and updates the service.

**By hand, if you want the service up before wiring CI:**

```bash
REPO=$(terraform output -raw ecr_repository_url)
aws ecr get-login-password --region eu-north-1 --profile my-pet-project \
  | docker login --username AWS --password-stdin "${REPO%%/*}"
docker build -f docker/airflow/Dockerfile -t "$REPO:latest" .
docker push "$REPO:latest"
```

Note that the ECS service carries `lifecycle { ignore_changes = [task_definition] }`. CI and Terraform would otherwise fight over the same field forever — CI points the service at a new digest, the next `terraform apply` points it back at whatever the Terraform-managed task definition says. The consequence to remember: **after the first CI deploy, Terraform is no longer the source of truth for which image is running.** `terraform apply` will not converge it back, and it is not supposed to.

## Step 7 — First run

There is no load balancer, so the UI address is the task's current public IP, and it changes whenever the task is replaced — which, on Fargate Spot, it will be.

```bash
TASK=$(aws ecs list-tasks --cluster airflow-cluster --service-name airflow-main-service \
  --query 'taskArns[0]' --output text --profile my-pet-project)
ENI=$(aws ecs describe-tasks --cluster airflow-cluster --tasks "$TASK" \
  --query 'tasks[0].attachments[0].details[?name==`networkInterfaceId`].value' \
  --output text --profile my-pet-project)
aws ec2 describe-network-interfaces --network-interface-ids "$ENI" \
  --query 'NetworkInterfaces[0].Association.PublicIp' --output text --profile my-pet-project
```

Open `http://<that-ip>:8080`. The scheduler container creates an admin user on first boot — see the entrypoint in [`ecs.tf`](../terraform/ecs.tf); the credentials are in plain sight there, and changing them is the first thing to do on any deployment reachable by anyone but you.

DAGs are paused at creation, so nothing has run yet. Do it in this order:

1. Unpause and trigger **`__test_dbt_integration`**. It runs `dbt debug` and nothing else. If the dbt venv, the Snowflake credentials injected from Secrets Manager, and the key-pair auth all work, this is where you find out — in ten seconds, instead of inside a five-task DAG.
2. Unpause **`air_pollution_snowflake_dag`** or **`weather_snowflake_dag`** and trigger one run. The `dbt build` task seeds `cities_config.csv` on the way through, because the seed is upstream of the fact table the run selects.
3. Check `RAW.AIR_POLLUTION` in Snowflake and the `bronze/` prefix in S3. They should agree.

## Tearing it down

```bash
terraform destroy
```

Two things will block it, both on purpose:

- **The S3 data lake has `force_destroy = false`.** Terraform refuses to delete a bucket with objects in it. Empty it first (`aws s3 rm s3://<bucket> --recursive`). The friction is deliberate — that bucket holds the only copy of the raw layer.
- **ECR refuses to delete a repository containing images.** Delete the images, or add `force_delete = true` if you are certain.

Worth knowing before you run it: the `RAW` database is Terraform-managed, so destroying it takes every dbt-built model with it. And the Secrets Manager secrets use `recovery_window_in_days = 0`, so they are deleted immediately rather than held for seven days — which means their names are free for reuse straight away, and also that there is no undo.

The Terraform state bucket is not managed by this configuration and survives.

## Known limitations of this deployment

Stated rather than discovered, because most of these are conscious trade-offs for a single-operator personal project, and a few are not.

- **The UI has no stable address and no authentication in front of it.** Access control is a security-group CIDR list, and the address changes with every task replacement. An ALB with a fixed DNS name is the obvious fix and has not been done.
- **The Airflow admin user is created by the container entrypoint with hard-coded credentials.** Acceptable only because of the point above; indefensible the moment the UI is publicly reachable.
- **One environment.** No dev/stage/prod separation, no Terraform workspaces, one state file. Adding a second environment today would mean copying, not parameterising.
- **State locking was only added recently** (`use_lockfile` in `main.tf`). If your working copy predates it, `terraform init -reconfigure` is required once.
- **`skip_final_snapshot = true` and `deletion_protection = false` on RDS.** The metadata database is treated as disposable, which it is here and would not be anywhere else.
- **Terraform stops owning the running image after the first CI deploy** — see the note on `ignore_changes` above.
- **Dead infrastructure is still in the configuration.** The bastion host and NAT gateway exist behind flags defaulting to off; removing them is the first step of the infrastructure phase in the [roadmap](../README.md#project-status).
- **Stopping after the first apply leaves a role trusting your own account root.** It grants nothing to anyone outside your account, but it is a placeholder, not a resting state.
